## 1. Release Theme

v26.9.1 is a **process-mining/OCEL manufacturing-pack expansion release, layered on an engine-registry and Reactor-pipeline hardening pass that is largely complete but not yet closed out.** The committed work since v26.8.30 finished ADR-0008's evidence-ranked multi-engine registry (`lib/ggen_igniter/discovery/`, `lib/ggen_igniter/stream/`, commits `01a6ef9`/`7a21a02`) and fixed the `mode:eval` Reactor `:render`-step crash (`0c0eb03`, `52164d6`). Concurrently, and still entirely uncommitted, seven new ggen-marketplace packs port ex4pm's process-mining reference implementations (incremental DFG discovery, sensor-to-event streaming, inductive-miner discovery, token-replay conformance, OCEL2/EKG derivation, OLAP slice/dice, and Chicago-style OTP fault injection) into reusable, namespace-parameterized `priv/ggen/*` packs with real Chicago-school test coverage. No v26.9.1 git tag exists yet — the version string appears only in commit messages (`d601983`, `8eb27cc`, `621f0ba`), so the first job of this document is defining what actually constitutes the v26.9.1 boundary.

## 4. Requirements Derived from New/Modified Tests

- The rendering pipeline (`Ontology.load!/1` → `Query.run/2` → `Frontmatter.split_template/1` → `Render.render/2`) must continue producing `Code.string_to_quoted!/1`-parseable Elixir for all seven new pack templates (`test/*_pack_test.exs` files).
- `mix ggen_igniter.sync --pack <name>` must continue to support real subprocess invocation for packs with no local fixtures, driven purely by `--engine sparql` (per `olap-pack`, `ocel2-ekg-pack`, `beam4pm-bench-pack` tests) — no dependency on the oxigraph NIF for these packs' CI-viable path.
- `mix ggen_igniter.doctor --pack <name>` must correctly surface pack-specific check numbers 9-12 passing (`test/process_discovery_pack_test.exs`), confirming doctor's pack-awareness generalizes beyond previously-tested packs.
- Generated modules must be genuinely reusable across differing namespace bindings with zero leftover hardcoded identifiers from the reference pack's default individual (explicitly re-verified for `chicago-fault-injection-pack` via a second render with `ex4pm_pro` bindings, and for `ocel2-ekg-pack` via asserting ontology-driven, not hardcoded, module/field names).
- A template requiring a consumer-supplied binding (`beam4pm-bench-pack`'s `wasm_adapter_module`) must fail fast (nonzero exit, no output file) when that binding is omitted, and must render correctly when supplied — this "load-bearing binding" contract should generalize to any future pack requiring consumer-supplied adapters.
- `GgenIgniter.Stream.Examples.SensorSink`'s `handle_message/2` must forward emitted events through a real supplied callback, asserted via `assert_received` — confirms Broadway-shaped stream sinks generated by this pipeline are testable without a mocking framework.
- Incremental (`update/2`) and batch (`from_events/1`) discovery paths must remain provably equivalent by construction (batch = fold of the same `update/2` step) — this is a structural invariant the test suite now locks in for `incremental-discovery-pack` and should be treated as a pattern for future streaming packs.

## 5. Requirements from ADRs

- **ADR-0007 (BLOCKED, unresolved as of ADR text):** `mix ggen_igniter.sync` unconditionally attempts the Reactor path but a real invocation raises `ArgumentError` from `Reactor.Executor.ConcurrencyTracker.allocate_pool/1` — "table identifier does not refer to an existing ETS table," likely a missing `:reactor` OTP-application-supervision start outside `mix test`'s app tree. **Must be root-caused and fixed, or explicitly re-verified as already fixed** given the repo's git log shows two follow-up commits (`0c0eb03`, `52164d6`) that may have addressed the related `mode:eval` crash but the ADR text itself is unedited and still names the ETS pool issue as separately open.
- **ADR-0007:** `GgenIgniter.Controller`'s own `use_reactor` dependency was not re-verified this pass — needs a fresh check.
- **ADR-0007:** `dispatch_pipeline/3` fallback (frontmatter with inline `sparql:` or `mode:eval`) still writes no receipt — disclosed, bounded-scope gap, not required to close for v26.9.1 but should stay documented as such rather than silently forgotten.
- **ADR-0008:** `docs/status.md` should be confirmed to carry a row for the evidence-ranked engine registry (findings suggest `7a21a02` already added one — verify it's accurate against the shipped shape, including the two disclosed deviations: `resolve/2` arity for `"all"`, SELECT-based qlever reachability probe instead of literal ASK).
- **ADR-0001:** the disputed oxigraph row-value-shape claim (raw N-Triples-style term strings vs. bare Elixir values) remains unreconciled between ADR-0001 text and independently-probed real behavior — the ADR explicitly does not resolve it. This should be closed (fix the ADR text, or fix docs/status.md's disputed claim per its own L167 finding) before v26.9.1, since it is a correctness-adjacent documentation contradiction, not cosmetic.
- **ADR-0003/ADR-001 (legacy):** three coexisting coordination pipelines (`Reconcile.run/1`, `ReconcileReactor`, `Sync`'s own inline path) remain unconsolidated — explicitly disclosed as future work, not a v26.9.1 blocker but worth a stated decision (see Open Questions).
- **ADR-0006/ADR-002 (legacy):** real AST-based structural injection (Sourceror/Igniter.Code zipper patching) remains unbuilt — standing, cross-referenced, not proposed for v26.9.1.
- **`docs/architecture/adr/README.md`:** the machine-generated ADR index table is stale — missing 0007 and 0008, and omits the legacy `ADR-00N` scheme entirely. Should be regenerated via `mix ggen_igniter.sync --pack adr-index-pack --engine sparql --out docs/architecture/adr/README.md` before release.

## 7. Open Questions

1. **What is the actual v26.9.1 commit boundary?** No git tag exists; "v26.9.1" and "v26.9.2" appear only inside commit messages (`d601983`, `8eb27cc`, `621f0ba`), and HEAD (`52164d6`) is unlabeled. Does v26.9.1 include the shell-hook work (`bb082a7`/`d601983`), the `--for-each`/inline-sparql Reactor routing (`8eb27cc`/`621f0ba`), the ADR-0008 engine registry (`01a6ef9`/`7a21a02`), the `mode:eval` fix pair (`0c0eb03`/`52164d6`), and/or the seven uncommitted process-mining packs — or is this a multi-release rollup that needs to be split?
2. **Is the Reactor pipeline going default in v26.9.1, or does `use_reactor: true` remain opt-in?** ADR-0007 discloses a real, apparently-unresolved-in-ADR-text ETS pool crash when `sync` unconditionally attempts the Reactor path — this must be answered before deciding whether Reactor-dependent features (receipt evidence, undo/4 compensation) can be relied on by default.
3. **Should the three coexisting coordination pipelines (`Reconcile.run/1`, `ReconcileReactor`, `Sync`'s inline path) be consolidated in this release**, or is that explicitly deferred past v26.9.1 (per ADR-0003's disclosed-but-unscheduled status)?
4. **Is oxigraph confirmed as the sole safe default engine**, given the still-unresolved ADR-0001 row-shape dispute? Does that dispute block trusting `--engine oxigraph` output shape for the new packs that were tested only via `--engine sparql` subprocess (olap-pack, ocel2-ekg-pack, beam4pm-bench-pack)?
5. **Are the seven new process-mining packs intended to ship as part of v26.9.1's user-facing surface**, or are they exploratory dogfood work (per this repo's CLAUDE.md parallel-agent protocol) that may be discarded, deferred, or need a real downstream consumer (e.g. beam4pm) before being called release-ready? The `beam4pm-bench-pack`'s `wasm_bench` template is explicitly PLANNED-pending a Wasmex adapter that doesn't yet exist in any real consumer.
6. **Does `to_prd_status/1` (PRD six-value status vocabulary mapping on `GgenIgniter.Receipt`) belong in v26.9.1?** It's explicitly named in the PRD (`~/.claude/plans/prd-ard-wiggly-creek.md:55`) and flagged in docs/status.md as the top PLANNED candidate — is this in scope for this release or a later one?
7. **Should `mix format --check-formatted`, `mix dialyzer`, and `mix credo --strict` be freshly re-run** before release, given docs/status.md flags all three as "not independently re-checked this pass" (cited from a prior pass)?
