# Idempotency & Verification Methodology (v26.11.10)

Formal specification of the two-run idempotency protocol, Igniter `--check` oracle integration,
and cryptographic tree hashing methodology enforced in `ggen_igniter`.

- **Release Version:** `26.11.10`
- **Idempotency Standing:** `IDEMPOTENCY_ALIVE` (Tree only)
- **Machine Evidence:** [evidence/receipt.json](evidence/receipt.json), [evidence/conformance.json](evidence/conformance.json)

---

## 1. Five-Part Idempotency Definition

Code generation cannot be considered production-ready if re-running the generator against an existing codebase alters files, introduces warnings, or generates duplicate definitions. `ggen_igniter` enforces a strict five-part idempotency contract:

```
+--------------------------------------------------------------------------------------------------+
|                                FIVE-PART IDEMPOTENCY DEFINITION                                  |
+--------------------------------------------------------------------------------------------------+
| (a) Zero file modifications : git diff after Run 2 is empty across all tracked files.            |
| (b) Zero unexpected files   : git status --porcelain shows no new untracked files after Run 2.   |
| (c) Deterministic exit code : Both Run 1 and Run 2 exit with code 0.                            |
| (d) Zero warnings emitted   : Run 2 emits zero compiler or runtime warnings.                     |
| (e) Cryptographic tree match: SHA-256 tree digest of Run 1 equals Run 2 (tree_T1 == tree_T2).   |
+--------------------------------------------------------------------------------------------------+
```

## 2. Why Igniter `--check` is the Essential Oracle

In standard Mix tasks, exit code alone is an unreliable oracle. Igniter's internal runner (`igniter.ex:1279-1281`) handles conflicts by returning `:issues`:

```elixir
# Igniter internal execution flow
defp do_or_dry_run(igniter, opts) do
  if igniter.issues != [] do
    print_issues(igniter)
    :issues
  else
    write_changes(igniter)
    :ok
  end
end
```

When `:issues` is returned, Mix treats it as normal execution and exits with code 0. Therefore, a generator could fail to write files due to collisions and still exit 0.

### The `--check` Invariant
When invoked with `--check` (`igniter.ex:1293-1330`), Igniter alters this behavior:
- Any pending file write, move, or deletion immediately halts the VM with exit code 1.
- Any unresolved issue or warning halts the VM with exit code 1.
- Any queued subtask halts the VM with exit code 1.
- **Exit code 0 under `--check` is guaranteed proof that the AST is identical and zero writes are required.**

## 3. The Two-Phase Two-Run Execution Protocol

Due to Ash's compilation architecture, resource generation requires application configuration (`base_resources`) to be pre-loaded in memory. Attempting to generate domains, resources, and base resources in a single pass leads to silent compilation short-circuits.

`ggen_igniter` structures generation into two explicit phases, each subjected to the two-run protocol:

```
[Phase 1: Base Manufacture]
  Run 1: mix <app>.manufacture --phase base --yes      (writes Repo, Config, BaseResource)
  Run 2: mix <app>.manufacture --phase base --check    (verifies 0 writes, exits 0)
         |
         v
[Phase 2: Core Manufacture]
  Run 1: mix <app>.manufacture --phase core --yes      (writes Domain, Resources, Actions)
  Run 2: mix <app>.manufacture --phase core --check    (verifies 0 writes, exits 0)
         |
         v
[Verification Gate]
  git diff --exit-code && sha256(Tree_T1) == sha256(Tree_T2)
```

### 3.1 Observed Verification Transcript (BookLibrary Fixture)
1. **Phase 1 Execution:**
   ```bash
   mix book_library.manufacture --phase base --yes
   mix book_library.manufacture --phase base --check
   ```

2. **Phase 2 Execution:**

## 4. Database State vs. Generated Tree Boundaries

A critical distinction in repository doctrine is the boundary between **source tree idempotency** and **database migration idempotency**:

1. **Source Tree Idempotency (`IDEMPOTENCY_ALIVE`):**
   - Covers files on disk generated by `Igniter.compose_task/4`.
   - Guaranteed byte-identical across repeated runs.
2. **Database Migration State:**
   - Running `mix ash.codegen` generates versioned migration snapshots under `priv/resource_snapshots/`.
   - If resource definitions have not changed, `mix ash.codegen` generates no new migrations.
   - However, executing `mix ash.setup` on a dirty or non-empty database involves external state (Ecto's `schema_migrations` table).
   - Therefore, `IDEMPOTENCY_ALIVE` is scoped to the **generated tree**. Database state idempotency requires isolated test fixtures.
